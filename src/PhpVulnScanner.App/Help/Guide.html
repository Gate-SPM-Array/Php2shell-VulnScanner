PHP Vuln Scanner

Portable Windows scanner that detects from outside, in a few seconds per target, the exposure to the two PHP runtime vulnerabilities published on 21 October 2026 (PHP2Shell, CVE-2026-109618 and CVE-2026-109619), and recognises upstream WAFs, CDNs, reverse proxies and load balancers.

1. Purpose and responsible use

The two vulnerabilities are flaws of the PHP engine, not of an application: any exposed PHP site is affected, in every version from 5.4 onwards, until the fix is installed (8.2.35, 8.3.36, 8.4.27, 8.5.12 or a distribution backport). The scanner takes the exposure inventory of a perimeter: who advertises a vulnerable version, who is protected by an edge barrier, who advertises nothing and must be checked on the host.

Responsible useScan only your own systems or with the owner's written authorisation. The program names itself in the User-Agent and leaves traces in the target's logs. It contains and runs no exploit code, does not change the state of servers and sends no request that drives PHP into memory exhaustion.

2. Quick start

  1. Extract PhpVulnScanner_v1.4_win-x64.zip anywhere (a USB stick is fine) and run PhpVulnScanner.exe. No installation, no runtime to install.
  2. Type the targets in the Targets box, check the ports (default 443) and the paths (/ and /index.php).
  3. Leave the alive check, level 2 and WAF detection on, or adjust them (chapters 4, 5 and 6).
  4. Press Start scan. The table fills as results arrive; double-click a row to see every piece of evidence for that target.
  5. At the end the HTML report is generated in the session folder; HTML report opens it in the browser, Export log… saves the log, CSV or JSON wherever you want.

4. Alive check

Before probing a target the scanner checks that it is alive, once per host, with the chosen methods in the order ICMP, TCP, UDP, stopping at the first confirmation.

MethodWhat proves itNote
ICMPAn echo reply.On Windows it uses the system API: no privileges needed. Many firewalls block it: the other methods then count.
TCPA successful connection or an explicit refusal (RST): in both cases the host is up.Usually the same ports as the scan.
UDPA reply with data or an ICMP port unreachable.Several ports, same syntax as the TCP field (e.g. 53,123). Silence proves nothing: the outcome stays "no response", never "down".

The methods start together and the check stops at the first confirmation: a silent host costs the longest timeout, not the sum. The time of every phase (alive, dns, tls, http-l1, http-l2, waf) is reported in the log, in the target sheet and in the report, so every millisecond is accounted for. Note on Windows: a connection to a closed port (RST) costs about 2 s because the stack retries the SYN before declaring the refusal; the scanner pays it once (TLS handshake) and does not attempt HTTP on the same port.

Continuous sweeper (v1.11). A separate task retries, at a slow pace and for the whole cycle, the hosts not confirmed alive (ICMP + TCP on the scan ports, timeout 1.5×, configurable lanes, default 4): whoever answers enters the running cycle at once and the "Not reachable" row is replaced. First round over every unconfirmed host; the next rounds only over hosts seen alive in the loop or known: the Known hosts field (Targets section, --known-hosts) takes the host_attivi_vX.Y.txt file of a previous session, and a known host that stays silent gets the KNOWN-HOST test in its sheet. The sweeper replaces the end-of-cycle second chance of v1.8-v1.10; --no-alive-retry turns it off. Operational rule: one instance at a time towards the same perimeter from the same IP, because a second instance's connections may be dropped by the perimeter and the host appear silent.

Cap and second chance (v1.8). Hosts in parallel (default 8) limits how many hosts are in alive check at the same time, whatever the thread count: every host opens ICMP, TCP and UDP together, and with 36 threads the initial burst timed out even live hosts (71 of 4094 against ~280). Second chance: unconfirmed hosts are retried once with ICMP + TCP on the scan ports and 1.5× timeout; those that answer are scanned in full and the "Not reachable" row is replaced (log: "Second chance: N hosts recovered"). Since v1.9 it starts as soon as the host queue is empty, served by the free threads; since v1.10 on 16 fixed lanes (with 6 threads v1.9 had 4: 35 min per cycle on the /20) and, from cycle 2 on, only for hosts seen alive at least once in the loop. Hosts that close the connection with RST during TLS (typical of an IPS) have, since v1.10, the reason "connection closed by the perimeter" and the test L1-RESET: the host exists, the service cannot be read. Probes cancelled after the confirmation are no longer awaited.

Per-host scheduling. The unit of work is the host: resolution and alive check once, then the ports in sequence, and the threads work on different hosts. In v1.2 the ports of the same host were adjacent in the queue and the threads waited together for the same alive check: on a /20 with four ports 75% of the time was waiting, not traffic. The alive check time is charged to the host's first row; the others state "run once per host".

The two boxes do different things: Check that the target is alive runs the alive check and records its outcome (Alive column, evidence, report); Skip targets not confirmed alive decides what to do with that outcome: on, an unconfirmed host gets "Not reachable" at once without attempting HTTP; off, the alive check is still recorded but the HTTP scan runs anyway (useful behind firewalls that block ICMP and only answer on the web port). With the first off, the second is disabled. The reason and the evidence list every configured method, in the configured order, with outcome and duration.

An invalid value in the numeric or port fields is never ignored silently: the scanner lists it before starting and writes it to the log.

5. The tests: level 1 and level 2

Level 1, passive (always on)

GET requests on the configured paths, no body. The scanner reads what the server advertises by itself:

  • X-Powered-By: PHP/x.y.z (written by PHP with expose_php=On) and Server: Apache/… PHP/x.y.z (mod_php with ServerTokens Full);
  • the PHPSESSID cookie, with a format check: an irregular session identifier is among the memory-disclosure indicators cited in public analyses;
  • PHP error messages in the body (display_errors on);
  • optionally, the revealing pages phpinfo.php, info.php, php.php, test.php (they only count when the body really is a phpinfo) and the PHP easter egg (?=PHPE9568F34-…), which reveals installations older than 5.5.

The version read is compared with the first fixed releases of its branch: 8.2.35, 8.3.36, 8.4.27, 8.5.12. Branches 5.4 … 8.1 have no official release: Debian, Ubuntu, RHEL, Plesk, cPanel and Sury fix without changing the number, so the number alone does not say whether the backport is installed.

Passive context: SAPI, operating system, application

From the same responses, with no extra requests, the scanner infers the SAPI (Server: Apache/… PHP/x = mod_php; nginx, LiteSpeed or Caddy in front of PHP = FastCGI/FPM or LSAPI; Apache with PHP but no PHP in the banner = not distinguishable; IIS = php-cgi), the operating system or distribution advertised in the banner or in the package suffix (Debian, Ubuntu, Win64…), which guides the backport check, and the application (over 50 signatures on meta generator, paths, cookies and headers: WordPress, Joomla, Drupal, phpMyAdmin, Nextcloud, Laravel, Moodle, GLPI, TYPO3, PrestaShop, Magento, Roundcube, Zabbix…), linked to the page of the NCSC-NL inventory of products with a PHP dependency, where the per-product status is updated over time. The PHP advisory names mod_php as the highest-risk case (execution before application code): that is why the SAPI weighs on the priority.

Application database. Besides the 50 built-in signatures, which take precedence, the scanner reads from the data\ folder the signatures of enthec/webappanalyzer (Wappalyzer format, over 7,600 technologies: headers, cookies, meta, html, scripts, URL, certificate issuer; signals that need a browser are excluded) and the NCSC-NL inventory (751 packages with a VEX status per CVE). From them it derives the application version when declared, the list of recognised technologies, a PHP evidence for every technology that implies it (WooCommerce → WordPress → PHP) and the product's NCSC-NL status per CVE (affected, fixed in x.y, not affected, under investigation). The data version (data\DATA-VERSION.txt) appears in the report and in the log; without the folder the program works with the built-in signatures only. To refresh the data: tools\build_appdb.py in the sources.

Light mode

With Light mode level 1 uses HEAD instead of GET (GET only if HEAD answers 405 or 501). Less traffic on large perimeters, but without a body PHP errors, phpinfo and the application cannot be read.

Level 2, preconditions and barriers

Small, inert POST requests on the main path, compared with each other:

  1. a url-encoded POST (a=1) and a minimal multipart POST with the same field: if the multipart is rejected (403, 406, 418, 429, 501, 503 or connection closed) and the url-encoded one passes, there is a multipart-specific barrier, the recommended measure for those who cannot update;
  2. if the barrier is there, eight Content-Type variants (upper case, no space, charset before the boundary, quoted boundary, space before the semicolon, extra parameter, tab…): a block comparing the exact string multipart/form-data can be bypassed and is reported as "partially blocked";
  3. a multipart with the PHP_SESSION_UPLOAD_PROGRESS field sent without a session cookie: PHP writes nothing without a session, so the test only says whether a WAF filters the field name;
  4. a multipart of configurable size (default 256 KiB) to discover edge size limits (413).
Why there is no exploitability testNo external scanner proves PHP2Shell exploitability. Tests that send large multipart bodies to drive PHP into memory exhaustion give the same answer on a fixed and on a vulnerable PHP (the fix repairs the cleanup after exhaustion, not the exhaustion itself: issue #1 of the Assetnote scanner), and on an unfixed worker the same request is the first half of the attack chain. By choice the scanner does not run them: where the version is not advertised the verdict stays "Undetermined" and the proof must be sought on the host (php -v, build date, package changelog, worker restart).

PHP "maybe": hints without proof (v1.5)

Between "PHP: yes" and "PHP: no" lies a band of signals that prove nothing alone but matter to whoever decides where to concentrate the checks. The scanner collects them with no extra requests, from the responses already received, and weighs them: strong 3, medium 2, weak 1; from 2 upwards the PHP column says maybe. Strong hints: the Expires: Thu, 19 Nov 1981 08:52:00 GMT header (the fixed date session_start() emits with the default cache limiter) and a cookie, whatever its name, whose value has the PHP session-id format (26 characters 0-9a-v). Medium: cookies of PHP frameworks and CMSs (laravel_session, ci_session, Drupal's SESS…, MoodleSession, fe_typo_user, OCSESSID…), X-Pingback, Link rel="https://api.w.org/", X-Redirect-By, X-Drupal-Cache, X-Generator headers, links or forms to .php, typical folders (/wp-content/, /sites/default/files/, /typo3conf/…), a handler treating the missing .php file differently from the others. Weak: robots.txt with Disallow on PHP paths, PHP's cache triplet without ETag/Last-Modified, a hosting panel (Plesk, cPanel, Webmin, CloudPanel), PHP-ecosystem technologies below the certainty threshold, certificate names mentioning wp, moodle, joomla. The weighted list is in test L1-HINTS, in the sheet and in the Suspected PHP section of the compact report; filter php:maybe.

Settings from the phpinfo page and CVE-2026-115560

When the scanner finds an exposed phpinfo() page (level 1 or extra tests), since v1.5 it reads the settings that matter for this family of vulnerabilities: session.upload_progress.enabled, session.serialize_handler, session.save_handler, expose_php, memory_limit, post_max_size, the Server API line (which settles the SAPI) and the version. Test L1-PHPINFO-INI: with upload_progress off the mitigation for CVE-2026-109619 and CVE-2026-115560 is in place; on, the host stays exposed to 115560 if the application switches the serializer at runtime. CVE-2026-115560 (PHP informational advisory of 23 October 2026) has no fixed release: "Fixed by version" refers to the two CVEs of 21 October; 115560 needs session.upload_progress enabled plus an ini_set('session.serialize_handler','php') before session_start() with php_binary or php_serialize in the configuration: conditions invisible from outside, to be checked on the host (php-fpm -i, grep of the code). The mitigation is the one already recommended: session.upload_progress.enabled=0.

Host talkativeness (v1.5)

A 0-5 index of how much the host tells about itself unasked: PHP and web server versions in banners, operating system, phpinfo page (2), directory listing (2), Apache/nginx/FPM status pages (2), debug pages with stack traces (2), readable composer.json/installed.json, .git/.svn/.env/backups, application version, TRACE allowed, internal names in the certificate. Not a vulnerability: it is the "information gathering" part vulnerability scanners have always done, put on a scale you can bring to a meeting. Test L1-VERBOSITY, a field in the sheet, the Talkativeness section of the compact report sorted by index.

6. WAF, CDN, proxies, load balancers

Every response is compared with a catalogue of signatures: headers (Server, Via, cf-ray, X-Akamai-…, X-Iinfo, X-Sucuri-…, X-Azure-Ref, X-Served-By…), affinity cookies (BIGipServer, AWSALB, ARRAffinity, citrix_ns_id, SERVERID…), block pages (only with an error status, so that an article about Cloudflare is not mistaken for Cloudflare) and the TLS certificate issuer. With the behavioural test the scanner adds a request with hostile-looking but inert parameters (compared with the normal request: a change of status or of the Server header means an active filter) and three repeated requests to observe differences between nodes (different Server headers or backend identifiers, different clocks, several addresses for the name).

Cross-host correlation. When the same behaviour (for instance "active filter: connection closed on hostile parameters") appears on most of the hosts with HTTP, with different web servers behind, the report says it once: it is almost certainly a single perimeter device (IPS or network WAF), not a protection of the individual hosts. In the reference /20 it concerned 80% of the hosts.

Every detection carries category (WAF, CDN, reverse proxy, load balancer), name, confidence (high, medium, low) and evidence. The confidence is an estimate: Server: nginx in front of PHP-FPM is the norm, not a proxy, and is reported with low confidence.

7. The verdicts and the priority

VerdictMeaningWhat to do
Vulnerable by versionAdvertised version of a supported branch (8.2 … 8.5) earlier than the fix.Update and restart all workers. If the number carries a package suffix, check the changelog: it may be a backport.
Likely vulnerableAdvertised version of an end-of-life branch (5.4 … 8.1) with a distribution suffix (7.4.3-4ubuntu2.29, 5.4.45-0+deb7u14): vulnerable by version, backport cannot be excluded.Check on the host; update or apply backports (Sury, rebuilt images, source).
Pure number on an end-of-life branch (7.4.33, 8.0.30, 8.1.14, no suffix): since v1.4 it is "Vulnerable by version", because a number without suffix comes from an upstream build (compiled, official image) and no distributor can have backported: the version says it all. The rule can be switched off in Advanced.
Mitigated at the edgeMultipart requests do not reach PHP (complete barrier on every variant).A stopgap: the update stays necessary; make sure the origin accepts traffic from the edge only.
UndeterminedPHP detected but no version advertised.Check on the host. The report shows whether multipart reaches PHP.
Fixed by versionAdvertised version equal to or later than the fix.Check that every worker was restarted; look at a bypassable multipart barrier if reported.
PHP not detectedAnswers HTTP but without PHP hints.If a proxy strips headers, PHP may still be there: check on the host.
Not reachableAlive check unconfirmed or no HTTP response.Check firewall and port; retry without "skip targets not alive".

The verdict always carries its reason with the evidence; in the target sheet (double-click, or the report) every test has outcome, detail, request sent and response received.

The priority is a derived remediation ordering, not a new verdict: Critical = vulnerable or likely vulnerable with mod_php and multipart reaching PHP; High = vulnerable with another or unknown SAPI; Medium = mitigated at the edge with a vulnerable version, or undetermined with multipart accepted; Low = undetermined behind a barrier, fixed with a bypassable barrier; None = fixed, no PHP, not reachable.

8. Discovered names and PHP surface

Discovered names and second pass

Scanning an IP address only shows the default virtual host: in a real /20 more than a third of the hosts with HTTP answered with a redirect or with the web server's courtesy page, and the real sites lived behind names. From every response the scanner collects the valid DNS names found in the TLS certificate (CN and SAN) and in Location headers ("glued" redirects such as https://www.example.orgindex.php, produced by a Redirect directive without trailing slash, are discarded). The names appear in the target sheet, in the report and in results.json: on their own they are already an inventory of the perimeter.

With Rescan discovered names every name (up to the per-host maximum) is probed again on the same IP and the same ports with Host and SNI equal to the name: no DNS resolution, no new target. The additional rows are called name @ IP and follow their address in the sort order. A wildcard *.example.org is not rescanned (it is not a name).

DNS check of Certificate Transparency names (v1.10). The names taken from crt.sh are every name of the domain that ever had a certificate, hosted on the IP or not: on the reference /20, 80% of the thread time went to rescanning names that did not live on the IP. Now a CT name enters the discovered names only if it resolves (A/AAAA, with the configured resolver) to the IP under test; if it resolves to another IP of the target list it is routed to that host; the others stay listed in the sheet (test ADV-HOST-CT-DNS) with no second pass. Checkbox in the PHP detection section, --no-ct-dns to turn it off.

Names in parallel (v1.7, redone in v1.8). The second pass does not run sequentially on the host's thread (10 names × 2 ports × 60-120 s kept one thread busy for 20-30 minutes): the pass uses workers with a priority queue, serving names first and new hosts next, and the host's closing (folding, final rows) starts when the last name finishes. Requests in flight stay as configured; IP rows appear in the table as soon as they are complete and are updated a few minutes later with the folded names.

Name folding (v1.4 and v1.5). Two rules avoid rows that say nothing new. The first (v1.4): a name returning the same content as the default vhost gets no row and goes into the Name column as "(= default vhost)". The second (v1.5): a name returning different content but the same outcome (verdict, version, SAPI, application and version, barrier, WAF, priority, PHP presence) as the IP row, or as another name row of the same IP and port, gets no row: the name goes into "(= same outcome)". This is the load-balanced farm with a shared certificate: ten names on five IPs produced fifty identical "PHP-FPM, no version, Undetermined" rows. A name revealing something different (a WordPress with a version, a different PHP, a different barrier) keeps its row. Folded observations all stay in results.jsonl and in the full report; in the compact report every row lists every name of the IP and port, uncut, because names are what you need to find the people who must act; nomi_scoperti_vX.Y.txt maps name → IP. Both rules can be switched off in the PHP detection section (--no-fold-names, --no-fold-outcome on the command line).

PHP surface

The configured paths are not enough to tell whether PHP is there: a site may serve its home page from a static cache and keep PHP only behind /login.php. With PHP surface level 1 adds, read-only:

  1. the missing-file probe, GET /<random>.php: 404 File not found. is the answer of PHP-FPM reached through Apache or nginx, No input file specified. that of php-cgi, a 404 page with X-Powered-By: PHP that of mod_php. It is a PHP signature independent of banner and application, and it also settles the SAPI. A 200 or a redirect on any path ("catch-all") is recognised and the following steps take it into account;
  2. about forty common entry points (login.php, wp-login.php, xmlrpc.php, administrator/, phpmyadmin/, adminer.php, typo3/, glpi/, roundcube/, webmail/, robots.txt, sitemap.xml…) with HEAD requests only: 200, 301, 302, 401 and 403 mean "exists";
  3. the .php files linked from the pages already downloaded (links, form actions, src), one level, on the same host.

The list appears in the Surface column, in the sheet and in the report. Level 2 uses the best discovered .php when the configured paths offer none that answers: the barrier is then measured where PHP really reads the body. Cost: 40 to 60 HEAD requests per answering host, diluted by the random delay of chapter 9.

9. Cycles, random order, pacing, estimate

Cycles. The same scan can be repeated N times with a pause between cycles, to watch a perimeter over time (hosts coming up, updates applied, barriers changing). Every log line, the status bar and the Completed tile say "cycle i of N"; Stop stops everything, even during the pause, and the completed results stay on disk.

Cycle outcome. Two ways:

  • One session per cycle: folders …_c1of4, …_c2of4, …, each with its own files and report; the Cycle column says which one each row belongs to.
  • Consolidation (default): a single session where, for every host/port (and name) pair, the most informative result wins and, since v1.8, the information only the other cycle has is united field by field (version, SAPI, application, barrier, certificate, WAF, lists of names, surface, technologies, exposures, hints), with verdict and priority recomputed, time and cycle of the latest observation and a MERGE test listing the fields taken: a declared version beats "undetermined", a reached host beats an unreached one, an observed barrier beats an untested one; ties go to the most recent cycle. The cycle history stays in the result (cycle 1: Not reachable · cycle 2: Likely vulnerable (7.4.33)): the Cycle column shows Δ 2/2 when the verdict changed between cycles, the report has a "Cycle history" section and counts the changes. Every observation, the losing ones too, stays in results.jsonl.

Random order and pacing. With Random order the hosts (and each host's ports) are visited in random order; the random delay between requests (min-max ms) and the requests-per-second cap dilute the traffic. They exist so that IDS and IPS do not trip even when the source address is whitelisted: scanning a /20 still produces thousands of connections and level 2 sends up to twelve consecutive requests to the same host. The order stays per host: the alive check runs once per host.

Estimate. The status bar shows pairs/s · cycle end hh:mm (+duration) · loop end hh:mm (+duration). The rate is that of the last 5 minutes (moving average updated every 2 s), not the average since the start: a network alternates slow zones of silent hosts with fast zones of immediate RSTs. Under one minute of data the estimate says "computing". The loop end is the projected current cycle plus the remaining cycles times the duration of the last completed cycle (or the projection) plus the pauses. With sequential order the estimate swings when the subnet changes; with random order it is stable. Every 5 minutes the log writes a "Progress" line with the current estimate: at the end you can measure how wrong it was.

10. Advanced: extra tests, pause, session merge

Since v1.4.2 everything about the PHP layer sits in one collapsible section, PHP detection: the paths, levels 1 and 2 with the probe multipart, the light mode, the surface, discovered names with the second pass and the folding of identical names, the pure-number rule and, at the bottom, the extra tests, one checkbox each, with the cost in requests per service in brackets. WAF, port pre-check, debug and report options sit in the WAF, engine and debug section. All of them are read-only (HEAD, GET, OPTIONS, one FastCGI management record); none sends a body, none downloads confidential content: exposures are recorded as existing, not fetched. None, Defaults (all but the browser User-Agent, Certificate Transparency and level 2 on every .php) and Maximum detection (every extra test plus level 2, surface, names with second pass, revealing pages and easter egg; turns the light mode off) are the shortcuts; the choices go into session.json and the report, and on the command line they are passed with --advanced.

TestWhat it looks for
HEAD vs GET, OPTIONSA HEAD next to the GET on the main path: differences in status, Server, X-Powered-By, cookies or length reveal a cache in front of the origin, a filter that only inspects GETs, a non-standard handler; the Allow of OPTIONS lists the methods (TRACE enabled is an exposure).
Composercomposer.json declares the "php" constraint: a certain minimum version even without a banner; vendor/autoload.php confirms a Composer application; vendor/composer/installed.json lists libraries and versions (and should not be public).
Status pagesApache /server-info lists the loaded modules (mod_php or mod_proxy_fcgi: SAPI for sure), /server-status version and vhosts, /nginx_status, the PHP-FPM status (/status, /fpm-status). Only pages in the expected format count, not any 200.
Application version filesWordPress readme.html, joomla.xml, Drupal CHANGELOG.txt, Moodle version.php, debug pages of Symfony, Laravel, Yii. The version is compared with the "fixed in" of the NCSC-NL inventory.
FastCGI 9000One FCGI_GET_VALUES record (management, harmless) on port 9000 of the host: an answer means php-fpm is exposed on TCP to the internet, a finding on its own.
PHP behaviours/index.php/something served as /index.php (PATH_INFO), the answer of xmlrpc.php, exposed sources (.phps, .php~, .bak: existence only), more revealing pages.
Level 2 on every .phpThe multipart barrier measured on every discovered .php (up to a maximum), not only on the main one: a WAF rule may be per path.
Browser User-AgentA second pass on the main path with a browser-like User-Agent that still contains the tool name: some WAFs and CDNs serve a different page to anything called "scanner". Off by default.
ComponentsFrom the pages already downloaded, no requests: WordPress plugins and themes, Joomla components, Drupal modules, TYPO3 extensions, with version when ?ver= is there. For whoever has to patch, it is the work list.
Accessory exposuresHEAD only on .env, .git, .svn, common backups and dumps, .htpasswd: existence only. On servers answering 200 to any path the test is skipped and says so.
More namesPTR of every alive host and the ServerName Apache writes in its error pages; optionally Certificate Transparency (crt.sh) for the discovered domains: no traffic to the targets, but requests to an external service. Off by default.

In the same section: names with the same content (a name that returns exactly the default vhost's response does not get a row: it goes into the Name column of the IP row; in the reference /20 it was 75% of the name rows), TCP port pre-check (all ports in parallel, TLS and HTTP only where the port answers: closed ports of alive hosts cost 22% of the time) and the pure number rule (chapter 7).

Pause. The button next to Stop halts the scan before the next host and the next request; in-flight requests finish and their results stay; paused time does not enter the estimate; a second click resumes. While paused the session folder and the report remain usable.

Merge sessions… Pick two or more session folders on the same ranges (hold Ctrl in the picker), even from different versions: the program checks the overlap of the targets and produces a new session …_phpscan_fusione where, for every service, the most informative result wins, with the history labelled by session, date and program version ("23/10 22:47 v1.2: Not reachable · 24/10 02:35 v1.3.1: Likely vulnerable"). The report has a Differences section: hosts alive in one session only, changed verdicts, information present in one and absent in the other. The original sessions stay untouched; the merge is a session like any other. From the command line: --merge folder1 folder2 --out folder.

Update data… Downloads from GitHub the webappanalyzer signatures and the NCSC-NL inventory and converts them into the data\ folder; the current files are replaced only when the download succeeds.

New in v1.6: certificates, cache, inventory, session id, budget

TLS certificate status. The certificate was already read but not judged. Every HTTPS service now gets a status (TLS-CERT, Certificate column, sheet and Certificates section of the compact report): valid, or the issues separated by semicolons: expired on …, not yet valid, expires in N days (within 30), self-signed, untrusted chain (checked offline against the root store of the scanning PC), name mismatch (only when the target is a name), RSA key below 2048 bits, SHA-1/MD5 signature. No effect on the PHP2Shell verdict: it says who must act and where.

Cache or intermediary in front of the origin. From Via, Age, X-Cache, CF-Cache-Status, X-Varnish, X-Served-By: test L1-CACHE, a row in the sheet. It explains why X-Powered-By and Set-Cookie may be missing and why HEAD and GET differ.

PHP versions declared in the body (outside phpinfo, e.g. a page printing "PHP/7.4.33"): recorded as a weight-2 hint and in the sheet, never in the verdict: text, not evidence.

Inventory. A CSV or JSON file (one row per system: target/ip/name/url, php_version, environment, owner, notes, application; separator , ; or tab; # lines ignored; CIDR networks and ranges accepted as target) given in the Inventory field or with --inventory. At the end of the scan the results are reconciled: the owner appears in its column and next to every service in the report; the Inventory section of the compact report lists different versions (declared against observed), declared but not observed (off, filtered, decommissioned or outside the list), observed but not inventoried (to be recorded or switched off) and PHP declared but not observed. Details in inventario_vX.Y.json. Reconciliation sends no requests: it works on the results.

Session-id adoption (extra test, off by default): one GET to the main path with a fresh random PHPSESSID; if the server adopts it instead of issuing its own, session.use_strict_mode is off (test ADV-SESSIONID). Runs only when the main path starts a session; a visit like any other, no user sessions, no login.

Per-service budget (default 120 s, 0 = none): beyond it the remaining optional probes (surface entry points, path-based extra tests) are skipped and recorded in the BUDGET test and in the sheet; level 1, level 2 and WAF are never skipped. In the reference /22 a dead backend answering 502 in one second cost 170 s per service.

Dead backend (catch-all 5xx). When the main page, index.php and the missing file all return the same 502/503/504 (since v1.7 pages answering with a redirect, typically /, are left out of the comparison), path probes are pointless: the surface stops (L1-SURFACE-PROBE says so) and the path-based extra tests are skipped (ADV-SKIP); HEAD/OPTIONS, components and host-level tests remain.

Session file writing. Up to v1.5 the periodic rewrite of results.json blocked every thread for its duration (with debug on a /20 it is hundreds of MB: in the reference /20 the 16 threads were busy on average 4-5). It now runs outside the lock, streaming, on a separate thread; results.jsonl is still written line by line. The load balancer "inferred from the Date header" now compares the gap between the node clock and the receive time, not the dates of responses taken at different moments.

12. Table, filters, sorting

  • The summary tiles are filters: one click shows only the rows of that verdict, a second click brings all of them back. Alive hosts counts the distinct hosts confirmed by the alive check (not host×port pairs: on a /20 with four ports the same machine appears four times) and a click shows their rows; with the alive check off it counts the hosts with at least one TCP, TLS or HTTP answer. The same number is in the report and in the closing line of the log.
  • Columns: Target carries only the IP address connected to; Name the FQDN (discovered name of the second pass, or the name entered when the target is an FQDN; "= default vhost" when a name returned the same content as the IP); Surface (number of discovered PHP paths, list in the tooltip and in the sheet); Cycle (cycle of the observation; with consolidation Δ marks a verdict that changed between cycles).
  • Since v1.5 the PHP column has three values: yes (proof: banner, PHPSESSID cookie, PHP errors, missing-file probe, an application that implies PHP), maybe (no proof but weighted hints, see chapter 5) and no. "Maybe" never changes the verdict, which stays "PHP not detected": it is an inventory of hints to decide where to look next. Since v1.7 "maybe" rows are highlighted in lilac and the PHP maybe tile counts them (services and hosts); since v1.8 the click adds it to the Verdict filter, OR-ed with the chosen verdicts.
  • Every row is a service (IP + port + name): a different PHP may answer behind a different port. The verdict tiles count services and, below, the distinct hosts ("on 9 hosts"); "Alive hosts" counts IPs.
  • The filter bar above the table combines the free text with four multi-select drop-downs (verdict, priority, alive, barrier): ticked entries inside one drop-down are ORed, drop-downs and text are ANDed. Clicking a verdict tile adds or removes that verdict in the drop-down; the counter says how many rows are shown; Clear filters resets everything.
  • Free-text syntax (since v1.5). A single word is a substring search over every field (IP, name, port, version, SAPI, application, WAF, reason, surface, technologies, exposures, OS). In addition:
    WriteMeaning
    7.1.4 apacheseveral terms = AND
    wordpress|drupal| = OR (binds tighter than AND: fpm wordpress|drupal = fpm AND (wordpress OR drupal))
    -nginxleading - = exclude
    reason:"weak hints"quotes for text with spaces
    field:valuerestrict to one field: ip, name, port, ver, sapi, app, waf, reason, surface, verdict, priority, alive, barrier, php (yes/maybe/no), tech, exposure, os, cycle (Italian names work too)
    ver:7.1.*, ip:192.0.2.21?.*, app:word*wildcards: * any sequence, ? one character; a term with wildcards is matched against the whole field (anchored), without wildcards it stays a substring
    ip:192.0.2.0/24, ip:192.0.2.10-50CIDR network or range, same syntax as the targets
    A malformed filter blocks nothing: the box turns red and the tooltip explains the error. Full example: verdict:vuln* | php:maybe -waf:f5 ip:192.0.2.0/23.
  • Click a column header to sort: the Target column follows the IP numbering (1, 2, 10, 100, not alphabetical order), with names at the end; port, priority, duration and start by real value. The same order applies to the report and to the CSV/JSON files.
  • The first column, Start, is the start time of the target's test in ISO format with milliseconds, 2026-10-22 16:07:12,243; the log shows local and UTC time on every line, 2026-10-22 16:07:12,243 (14:07:12,243Z).

13. Command line

The same executable runs without a window, for scripts and scheduled tasks:

PhpVulnScanner.exe --scan targets.txt --ports 443,8443 --out D:\scans --label customer --quiet
PhpVulnScanner.exe --scan 192.0.2.10,www.example.org --no-alive --light --json result.json
PhpVulnScanner.exe --scan 192.0.2.0/22 --cycles 4 --cycle-pause 300 --random --delay 50-250 --rate 20 --threads 8
PhpVulnScanner.exe --help

Options (v1.10: --config, --save-config, --analysis-bundle, --no-ct-dns): --ports, --paths, --out, --label, --no-alive, --no-icmp, --alive-tcp, --alive-udp, --alive-timeout, --scan-not-alive, --no-level2, --no-waf, --light, --threads, --connect-timeout, --read-timeout, --resolver, --host-header, --json, --csv standard|excel, --quiet; since v1.3 also --cycles N, --cycle-pause s, --consolidate (default) or --separate-sessions, --random, --delay min-max (ms), --rate n (requests/s), --no-surface, --no-names, --no-rescan-names, --max-names n, --debug, --report-unreachable; since v1.4 --advanced all|none|keys (keys: headvsget, composer, status, appversion, fastcgi, behaviours, level2all, browserua, components, exposures, ptr, ct), --no-fold-names, --no-fold-outcome (v1.5), --inventory <file>, --budget <s> (v1.6), --no-precheck, --no-pure-version, --merge folder1 folder2 … --out folder (session merge, no scan). Session folder and report are the same as in the interface; with separate sessions, one report per cycle.

Exit codes: 0 none vulnerable; 1 at least one "vulnerable by version" or "likely vulnerable"; 2 invalid arguments; 3 "undetermined" only; 4 scan stopped or failed. In PowerShell: & .\PhpVulnScanner.exe --scan ... ; $LASTEXITCODE.

14. Declared limits

  • Invisible backports. The version number does not reveal distribution backports: "Likely vulnerable" and the package suffix must be checked on the host.
  • No proof of exploitability. See chapter 5: the verdict stops at the version and the barriers.
  • WAF and CDN instead of the origin. Headers may be rewritten and the multipart block may only apply to traffic through the edge: the origin stays exposed if reachable directly (TLS certificates and historical DNS reveal it).
  • UDP. Silence does not mean the host is down.
  • One path. Level 2 tests concern the main path (configured or discovered): other paths may have different rules.
  • Discovered names. Only the names the server itself reveals (certificate, redirects): virtual hosts that appear nowhere stay invisible; passive DNS or inventories are needed.
  • Estimate. It is a projection of the recent rate: a zone of silent hosts or a subnet change can move it a lot.
  • SAPI, operating system and application are hints from the banners: a proxy that rewrites headers hides or distorts them; the priority inherits that uncertainty.
